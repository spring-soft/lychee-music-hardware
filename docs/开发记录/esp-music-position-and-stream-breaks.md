**2026-09-25 修的三个 bug，是用户报"偶发卡顿"的真正原因。** 三个都在"位置/断流"这一片，
一起记，因为都是"看起来像卡顿、其实是逻辑错"。

## 1. ⚠️⚠️ `audio_engine_position_ms()` 32 位溢出：**97.4 秒以上的歌位置会回绕**
```c
return base + (f - BOARD_I2S_DMA_FRAMES) * 1000 / s_fs;   /* 全是 32 位 */
```
`f` 是已交给 DMA 的帧数，到 **4,294,967 帧（44.1kHz 下只有 97.4 秒）** 时 `f * 1000`
就超过 uint32 上限 → 位置每 97.4 秒回绕一次。
**实测数值完全对上**：续播基准 61.4s + 真实播放 106.6s → 算出 70.6s，观测值 69.7s ✓

后果全都是"看起来像卡顿"：**进度条回跳、歌词错位、seek 跑偏、"断流续播"跳到错的地方**、
以及**歌还没放完就被判成"放完了"**（因为位置比时长短了）。
修法：`uint64_t df = (uint64_t)f - BOARD_I2S_DMA_FRAMES; return base + (uint32_t)(df*1000/s_fs);`
`audio_engine_decoded_ms()` 和几处日志里的同一算式一起改了。

**教训**：凡是要把"帧数/字节数"换算成毫秒的地方（`x * 1000 / rate`），先想一下
`x` 能到多大 —— 几百万帧在 44.1kHz 下只是几十秒，32 位不够。
同类算式这个工程里还有几处（`duration_s * 1000`），都顺手加了 64 位保险。

## 2. ⚠️ 断流时的"流已结束"标志让引擎走了**正常播完**的路
`fetch` 任务在网络读取出错时同时置 `s_error` 和 `s_fetch_eof`，于是 out 任务把它当
"流读完了" → `AE_STATE_FINISHED` → **播放器看到 FINISHED 就"下一首"**
→ 用户听到的是**"歌放一半突然跳走"**。（我第一版改在 ERROR 分支，根本没走到。）

**修法**：在播放器的 FINISHED 分支里用 `audio_engine_is_error()` 再分一次：
- 出错 + 位置离结尾还远 → **从当前位置接着放**（`start_index_from(idx, pos)`，
  位置由 DMA 帧数推导、可信；Navidrome 对转码流支持 timeOffset）
- 出错 + 位置已经在结尾 3 秒内 → 这才是真的播完 → 下一首
- 没出错 → 正常播完 → 下一首

⚠️ **第二种情况是必需的**：Navidrome 的转码流**收尾时连接是被【复位】的**（不是正常关闭），
所以每首歌结束时读出来也是"错误"而不是 EOF —— 不判的话会在歌尾反复"续播"，永远进不了下一首
（实测到"位置 133953 / 总长 134000"还判成断流，死循环）。
判据：`dur > 0 && pos + 3000 >= dur` → 当它唱完了。
⚠️ 位置必须在 `start_index_*` **之前**读：那里面会 `audio_engine_stop()` 把基准清掉。

## 3. 断流的真实频率与"加缓存没用"的结论
实测（6 分钟串口采集）：
```
[速率] 网络取流 23 KB/s ｜ 解码消耗 23 KB/s ｜ ring_in 128 KB / ring_pcm 112 KB
```
**取流速率正好等于消耗速率、两个缓冲一直是满的** —— 服务器和缓冲都不是瓶颈。
真正发生的是**大约每 5 分钟连接被对方关掉一次**（`读取错误 (-1)` → `tcp_read error`），
而且刚好在**每首歌的结尾**也会复一次位。

**用户问过"加大缓存能不能改善"：不能。** 现有缓冲合计约 **6.4 秒**
（ring_in 128KB≈5.5s + ring_pcm 128KB≈0.74s + DMA 139ms），
而断流是"连接没了"，加缓存只是把"能忍 6 秒"变成"能忍 10 秒"。
**正确的做法是"断了就接着放"**（上面的第 2 条），代价只有约 1 秒重连。

**顺带留下的长期诊断**（`sdkconfig` 里没有开关，一直开着）：
每 30 秒一行 `[速率] 网络取流 X KB/s ｜ 解码消耗 Y KB/s ｜ 已播 N ms ｜ ring_in/ring_pcm/DMA`，
**一有欠载就当场打一行**（事后再看计数器会因换歌归零）。
判读基准：源是 mp3@192k → 需要 **24 KB/s**。

## 4. 验证手法
前面几轮都是"改完让用户按一遍"，这轮开始用固件的**自检开关** +
长跑采集（`K4_SELFTEST` 见 [[esp-music-m4-keys-player]]）：
- 位置是否单调：采 `heartbeat` 里的 `pos=` 序列，看有没有回绕
- 断流处理：grep `本首播完 / 流被掐断 / 流刚起就断`
- 是否真的流畅：`欠载 #` 一次都不该出现
