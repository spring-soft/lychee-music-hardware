# ESP-Music：纯原生音乐终端（脱离 esp-claw，从零新建工程）

## Context — 为什么做这件事

现在这台 ESP32-S3（ESP32-S3-COREBOARD V1.4 + ES8388/PAM8406 音频板 + ST7735 屏 + K1–K4）上的音乐功能，跑在 **esp-claw 框架**的 Lua 技能里（源码 `/home/lychee/esp32s3-backup/k3_voice_chat_music/`，部署在设备 `/fatfs`）。

踩到的坑**全部来自框架**：Lua 200 local 上限导致脚本被迫分片、`SKILL.md` 超限让 `app_claw_start` abort（只能重烧）、主循环缺延时饿死 LVGL、**GMF 音频组件内存破坏 bug 导致 FLAC 直传必崩**、`managed_components` 的 4 处手改补丁一拉依赖就丢。实测现在 esp-claw 固件已把 **app 分区吃到 93%**（3.46MB / 3.89MB）。

用户决定：**另起一个纯原生 ESP-IDF 工程**，只保留「本地播放 + 屏幕按键 UI + 蓝牙遥控」，并新增一个**网页控制台**；不做语音对话(ASR/AI)与 IM 通道。设备定位从「AI 助手」变成「纯音乐终端」。

```yaml
  espressif/mdns: "~1.13.1"               # esp-music.local

```

**7 条已核实、会改变实现方式的事实**（实现时必须遵守）：

1. `esp_codec_dev` 1.6.2 的 `es8388_open()` 写 `0x2E/0x2F=0x1E(0dB)` 但 **`0x30/0x31=0x00(-30dB)`**；`esp_codec_dev_set_out_vol()` 只动数字音量 `0x1A/0x1B` → **混合音量必须自己直写 `0x2E–0x31` 四个寄存器，且每次 `esp_codec_dev_open()` 后必须重新施加**（open 会清掉）。
2. I2C 地址填 **0x22**（8 位形式），且 `CONFIG_CODEC_I2C_BACKWARD_COMPATIBLE=n` 时要传 `bus_handle`。
3. ES8388 的 I2C 写入会**静默失败**（用户自己的原生测试已证明：MASTERMODE 会变成 0x80 → 完全无声）→ 初始化必须"**写→读回→重试 8 次**"并统计重试次数。
4. **S3 没有硬件 ASRC** → ❌ 纠正我之前的说法：**主路径不做重采样**，改为首次拿到采样率时**重配 I2S 时钟**（`i2s_channel_reconfig_std_clock/slot` + 重开 codec + 重新施加音量）；软件重采样只作退路。
5. IDF 5.5.4 **无内置 st7735 panel 驱动**、`esp_lvgl_port` 也不在缓存里 → 用 `waveshare/esp_lcd_st7735` + **自写约 90 行 LVGL port**。
6. LVGL 9.6.0 有 `lv_binfont_create_from_buffer()` → 字体可零拷贝从 flash mmap 加载，RAM 占用约 0。
7. 字体源用 `/usr/share/fonts/truetype/droid/DroidSansFallbackFull.ttf`（**单面 TTF**，全 CJK；系统里 Noto CJK 是 `.ttc`，`lv_font_conv` 读不了）。注意它 ASCII 是**全角**，子集要排除 ASCII，靠 fallback 到 `lv_font_montserrat_*`。本机已装 Pillow 10.2.0，PNG→RGB565 与字体退路都能纯 Python 离线做。

## 分区表（16MB，总和正好）

**分区表偏移刻意对齐 esp-claw**（表在 0x9000、nvs 在 0xA000，而不是 IDF 惯例的 0x8000）：这样新旧固件占用的是同一批 flash 区域，不会留下"残表"；将来整片还原 esp-claw 就是一条命令。设 `CONFIG_PARTITION_TABLE_OFFSET=0x9000`。

```csv
# Name,     Type, SubType, Offset,   Size
nvs,        data, nvs,     0xA000,   0x6000,     # 24K 配置（与 esp-claw 同位置）
otadata,    data, ota,     0x10000,  0x2000,
phy_init,   data, phy,     0x12000,  0x1000,
ota_0,      app,  ota_0,   0x20000,  0x300000,   # 3M 主固件（与 esp-claw app 同起点）
ota_1,      app,  ota_1,   0x320000, 0x300000,   # 3M OTA 备槽（以后改 UI 走 WiFi 升级）
assets,     data, spiffs,  0x620000, 0x200000,   # 2M 预渲染图/字体/网页
cache,      data, fat,     0x820000, 0x7E0000,   # 7.875M 封面/歌词/最近/收藏
```

**资产与网页放分区 + mmap，不嵌进 app**：改一行 HTML 或一张图只需烧 700KB，且 mmap 指针可直接当 `lv_image_dsc_t.data` 和 `httpd_resp_send_chunk()` 的源（零拷贝）。构建期用 IDF 自带的 `esptool_py_flash_to_partition()` 注册烧写。唯一禁忌：mmap 指针不能直接交给 SPI DMA（LVGL 会先绘进 RAM 的 draw buffer，所以走 LVGL 就没事）。

## 任务模型（S3 双核；WiFi/BT 协议栈默认钉 core 0）

| 任务 | 核 | 优先级 | 栈 | 职责 |
|---|---|---|---|---|
| `audio_out` | **1** | **19** | 4K | `ring_pcm` → `esp_codec_dev_write()`；统计 `frames_queued`、underrun |
| `key_dispatch` | 1 | 12 | 3K | 按键事件 → `music_cmd_t` 分发 |
| `audio_decode` | 1 | 8 | 8K | `ring_in` → `esp_audio_simple_dec_process()` → 归一化 → `ring_pcm` |
| `ui_lvgl` | 1 | 5 | 8K | `lv_timer_handler()` + 10ms 睡眠；页面切换/局部刷新 |
| `audio_fetch` | **0** | 6 | 6K | HTTP 读 → 直接写进 `ring_in` 空闲区（零拷贝） |
| `httpd` / `net_mgr` / `meta_fetch` / `cover_decode` | 0 | 5/5/4/3 | — | REST、WiFi、元数据、封面解码 |
| NimBLE host | 0 | 21 | — | 广播/连接/HID report |

**避免 UI 卡顿的四条硬措施**：① 音频路径优先级严格高于 UI；② **解码任务每帧 `vTaskDelay(1)`**，把 UI 最坏延迟钉在 1 tick（不做这个，解码会连跑满缓冲才让出，UI 最长停顿约 700ms —— 这正是老实现"忙死"的形态）；③ 网络/TLS/JSON/JPEG 全在 core 0，不跟 UI 抢核 1；④ 运行时**绝不创建/销毁 widget**（4 个页面 + toast 开机全建好，切换只改 `HIDDEN` 标志和图像 src），避免碎片化。

**缓冲**：`ring_in` 128KB（沿用实测有效的预取量）+ `ring_pcm` 128KB，都在 PSRAM；I2S DMA `6×1024 帧 ≈ 139ms`（**抗 WiFi/BT 尖峰的真正主力**）。ring 提供 `read_span_or_pack()` —— 数据绕回时把尾部 memmove 到头部，保证解码器总能拿到连续帧（`esp_audio_simple_dec_process` 只能吃连续 buffer，这是最容易踩的坑）。所有阻塞等待都用 100ms 超时循环 + 检查**代际号 `gen`**，切歌时立刻退出而不是傻等。

**代际号**：每次切歌 `gen++`；封面/歌词/元数据等异步结果带 `gen`，回来时 `gen` 不符直接丢弃 —— 否则快速连按"下一首"必然封面串台。

## 音频管道

**初始化序列**（`board` 组件）：PA 使能(47) → I2C 新驱动(`i2c_new_master_bus`) → I2S TX(`i2s_new_channel` + `i2s_standard_philips`，16bit/stereo/MCLK=256×) → `esp_codec_dev` 包装 ES8388（**addr=0x22**）→ `esp_codec_dev_open()` → **`board_vol_apply()`（必须在 open 之后）**。

**混合音量**（自己实现，实测"变干净了"）：

```
percent → 目标衰减 dB（0%→-60dB, 100%→0dB）
衰减 ≤30dB : 用模拟音量 0x2E–0x31（0x1E=0dB, 0x00=-30dB），数字音量 0x00
衰减 >30dB : 模拟置 0x00(-30dB)，超出部分用 esp_codec_dev_set_out_vol() 降数字
★ 0x2E/0x2F/0x30/0x31 四个都要写（0x30/0x31 若漏写，走 LOUT2/ROUT2 的耳机白掉 30dB）
```

按键连调音量不要每次都写 I2C（写+读回校验约 2–4ms）：UI 只更新 `target_vol` 原子量，由 `audio_out` 每 100ms 检查差异后再写。

**播放/换曲/seek**：`/rest/stream?id=..&u=..&t=<md5(pass+salt)>&s=<salt>&v=1.16.1&c=esp-music&f=json&format=mp3&maxBitRate=192[&timeOffset=<s>]`（**必须显式 `format=`**，只给 `maxBitRate` Navidrome 会默认给你 **Opus**）。解码循环处理三种返回：`BUFF_NOT_ENOUGH`→按 `needed_size` 扩容重试（**FLAC 单帧远大于 MP3，绝不能按 MP3 定死 16KB**）、`DATA_LACK`→等更多输入、`OK`→commit + 归一化(mono→stereo / 24,32bit→16bit)后写 `ring_pcm`；FLAC 需 `raw.eos=true` 收尾才不丢尾帧。

**格式嗅探**（不依赖 URL 扩展名，老实现就栽在这里）：peek 前 8KB 判 `ID3`/`FF Fx`→MP3、`fLaC`→FLAC、`OggS`→Vorbis、`RIFF..WAVE`→PCM、`FF F1/F9`→AAC、`ftyp`→M4A，都不匹配就按 MP3→AAC→FLAC 顺序试 `open()`。判定结果 + 前 16 字节 hex + `sample_rate/channel/bits` 一起打日志。

**真实播放位置**（这是"必须可信"的核心）：

```
audible_frames = frames_queued - dma_depth(6144 帧)      # 只可能在 write 成功后累加
position_ms    = base_ms + audible_frames * 1000 / sample_rate
```

由**已交给 DMA 的 PCM 帧数**推导，不是墙钟 —— 网络卡顿/任务抢占/暂停都不会让它漂移或跳变，且单调递增；暂停时继续写静音但不累加（位置冻结）。每 10s 打一条自检日志跟手机秒表对账（偏差应 <200ms 且不累积）。

**seek**（Navidrome 只在"真转码"分支尊重 `timeOffset`，否则回落到 raw + **静默忽略** `timeOffset`，表现为"seek 后从头播"）：

```
if (Content-Length == getSong().size 或 Accept-Ranges: none → 说明没转码)
     → 走 Range: bytes=<推算偏移>-（FLAC 用帧头 sample number 反算精确位置；MP3 按 CBR 估算，误差 1–3s）
else → 新请求加 timeOffset=<秒>（OpenSubsonic transcodeOffset 扩展）
esp_audio_simple_dec_reset() → frames_queued=0 → gen++ → 恢复
```

每次 seek 都打日志记录**实际走了哪条 + 返回码 + Content-Length**，这是排查 seek 问题的唯一线索。

**解码器开关**：只开 MP3/AAC/FLAC/PCM（Vorbis 视需要），其余全关省体积。默认配置 `transcode=mp3@192k`（服务端转码，格式永远简单可靠、seek 最省事），FLAC 直传作为高级选项 —— 出问题不影响主流程。

**WiFi**：播放中 `esp_wifi_set_ps(WIFI_PS_NONE)`，空闲 30s 后恢复 `MIN_MODEM`。

## 存储

**NVS**（namespace 分组，key ≤15 字符）：`net/{ssid,pass,ap_ssid,ap_pass,ap_on,hostname}`、`nd/{host,user,pass,transcode,maxbr,insecure,ok}`、`ui/{vol,dmode,bright,gapx,gapy,mirror,swap,invert,bgr}`、`play/{src,srcid,lastid,lastpos}`。

**FATFS（`cache` 分区 + wear levelling）**：`recent.json`（最近 50 条，**10s 去抖**落盘）、`starred.json`、`playlists.json`、`cover/<id>.565`（72×72 RGB565=10,368B，上限 300 个）、`lrc/<id>.json`。超限按 mtime 删到 80%。不用 NVS 存列表（反复写大 blob 磨损快、原子性差）。

## 网页控制台

**REST API**（`/api/*`，无鉴权）：`status`（含 state/pos/dur/vol/queue/net/bt/gen）、`play`/`pause`/`resume`/`toggle`/`next`/`prev`/`seek`/`volume`、`sources`/`source`/`queue`/`queue/play`/`queue/append`、`playlists`/`search`、`starred`/`star`/`recent`、`cover/<id>`（**必须代理**：AP 模式下手机没有到 Navidrome 的路由，也不暴露凭据）、`lyrics/<id>`、`config`（GET/POST，POST 保存前先 `ping` 校验）、`wifi/scan`（**异步，绝不在 httpd 任务里阻塞 4 秒**）+ `wifi/scan/result` + `wifi`（不重启生效）+ `wifi/status`、`ap`、`display`（屏幕校准）、`hid`、`debug`（堆水位/任务栈/underrun/i2c_retries）。

**状态推送：1000ms 轮询 + 前端本地插值**（不做 SSE/WebSocket）。`/api/status` <1KB，1s 一次对局域网无压力，且手机休眠回来不用重连。进度条流畅度靠前端用 `performance.now()` 每 100ms 外推，切歌靠 `gen` 重置。**不要**为"求流畅"把轮询降到 250ms（会让 httpd 频繁醒，反而干扰音频）。

**前端**：`assets_src/web/index.html` 单文件、**浅色系**、内联 CSS/JS/SVG、**零外部引用**（AP 模式无 DNS/公网，任何 CDN 都会白屏）。分块：状态条 / 播放器卡（封面+歌名+进度可拖+控制+音量+收藏心形）/ 来源 Tab（最近·收藏·随机30·歌单）/ 歌曲列表 / 搜索框（debounce 400ms）/ 设置面板（Navidrome、WiFi 扫描点选、SoftAP 开关、显示校准、HID）/ 断连横幅。`gen_assets.py` 同时产出 `index.html.gz`（约 9KB），按 `Accept-Encoding` 发送。

## UI 实现（浅色系）

**页面结构**：`scr_play`（bg_img 预渲染底图 + topbar 符号/歌名 + cover 72×72 + lyr_box 3 行 + prog_track/prog_bar + 时间 + toast）、`scr_list`（5 行 + 高亮条 + 正在播标）、`scr_menu`（6 行窗口）、`scr_vol`。切换用 `lv_screen_load`（4 屏全预建），**显示模式切换不换屏**，只改 `HIDDEN` + 换底图 src。

**预渲染资产清单（约 262KB，全部进 assets 分区）**：`bg_play_a/b/c`（160×128×3）、`bg_list`、`bg_menu`、`bg_vol`（各 40,960B）、`hl_row`(160×20)、`hl_menu`(160×16)、图标 10×10 ×11 个、`placeholder_cover`(72×72)。流程：`gen_ui_png.py` 用 PIL 按固定坐标画底图（**代码可复现，改设计改脚本**）→ `gen_assets.py` 打包 RGB565 小端 + 生成 `assets_index.h`。

**中文字库**：`lv_font_conv` 生成 LVGL bin 字体 → 放 assets 分区 → `lv_binfont_create_from_buffer()` **零内存占用**。字形集 GB2312 一级 3755 字 + 标点，**16px / 2bpp ≈ 270KB**；fallback 到 `lv_font_montserrat_14`（ASCII 走它）。退路：`gen_font_pil.py` 纯 PIL 生成 LVGL C 源（编进 app，+270KB），或 `LV_USE_FREETYPE` + `esp_lv_fs`（assets 扩到 5MB）。

**避免整屏重绘的三条硬规则**：① 底图用 `lv_image`，只在切页/切模式时换 src；② 所有动态元素**小面积**且**父对象无填充/无圆角/无阴影**（圆角+阴影会把重绘区扩到整块，这是 LVGL 最常见的性能陷阱；视觉圆角由预渲染底图提供）；③ 定时器里先比较再 invalidate。进度条 4Hz 更新（`lv_bar_set_value(..., LV_ANIM_OFF)`，重绘面积 912B≈0.2ms）；歌词 200ms 检查行号，只在 `idx` 变化时改文本（重绘 7KB≈1.5ms）。

**歌词**：`getLyricsBySongId`（OpenSubsonic，**毫秒级 `line[].start`**）→ `idx = upper_bound(lines[].t <= pos_ms + user_offset_ms) - 1`，位置来源就是上面的真实位置，所以**歌词与声音天然对齐**；菜单给 ±0.5s 微调（存 NVS）。无同步歌词时（`synced=false`）按行数均分时长做匀速滚动并标注。`getLyrics`（artist+title）只作兜底（会串歌）。

**屏幕校准**：ST7735 有 green-tab/red-tab 差异，把 `gapx/gapy/mirror/swap/invert/bgr` 全做成**运行时可变**（NVS + 菜单 + `/api/display`），改完立刻 `esp_lcd_panel_set_gap/mirror/swap_xy/invert_color` 生效 —— 第一次点屏就不用反复改代码重烧。

## BLE HID 遥控

`esp_hid` + NimBLE：`nimble_port_init` → GAP `ble_svc_gap_device_name_set("ESP-Music Remote")` → `esp_hidd_dev_init(ESP_HID_TRANSPORT_BLE)`。Report Map 用 Consumer 位掩码（play/pause 0xCD、next 0xB5、prev 0xB6、vol ±0xE9/0xEA、mute 0xE2、stop 0xB7、FF/RW 0xB3/0xB4）；发送用 `esp_hidd_dev_input_set()` + 20ms 后发**释放**（否则主机当长按）。配对用 `BLE_SM_IO_CAP_NO_IO`（Just Works）；若某主机强制 MITM，改 `DISP_ONLY` + `sm_mitm=1` 并在 LCD 上显示 6 位 passkey（我们有屏幕，很划算）。**WiFi 必须先于 BT 初始化**；`CONFIG_SW_COEXIST_ENABLE=y`；若播放中出咔哒声改 `ESP_COEX_PREFER_WIFI`。**BLE 失败必须非致命**（只置 `bt.available=false`，播放完全不受影响）。

# M8：屏上搜索（字母键盘 + 拼音输入法）+ 导航规则统一

## Context — 为什么做这个

用户要求在设备上直接搜歌。需求原话拆解：菜单里加搜索（**取代原来的"播放/暂停"项**）→
选搜索方式 → 输入 → 看结果 → 选一首播 → K4 回上一级；同时把全机的 K4 规则统一成
**短按回上一级、长按回播放器**。

**关键约束是"中文"**，这一点实测过、也查过：
- 屏上键盘只能打 A-Z，**打不出汉字**；
- Navidrome 服务端**不支持拼音搜索**（实测 `yue`/`ylkbd`/`zjl`/`caijianya` 全部
  返回 0 结果；官方也没有这个功能，第三方镜像做的只是简繁转换）；
- 而**模糊搜索本身是好的**（搜「不懂」能找到「越来越不懂」，实测 2 首）。

用户明确否掉了"设备本地建拼音索引"这条路 —— 理由很实在：**他还会继续往曲库加歌，
本地索引会过时**。

所以采用：**屏上拼音输入法**（把字母在设备上变成真汉字，再把汉字交给服务器搜）。
好处正是用户要的：**搜索始终是服务器做的，新加的歌立刻能搜到，不存在索引过时**。

拼音数据不用联网找，本机就有：用户的中文输入法是 Rime 雾凇拼音，
`~/.local/share/fcitx5/rime/cn_dicts/8105.dict.yaml`（通用规范汉字表）是
`汉字<TAB>拼音<TAB>权重` 的纯文本 —— **权重正好用来给候选字排序**，不用自己猜常用度。

**已实测的数据可行性**（离线算过）：
- 与本机字库（`assets_src/font/charset.txt`，6763 个汉字）取交集 → **覆盖 6653 字（98.4%）**
- 407 个音节、7153 条候选；候选最多的是 `yi`（109 个）
- `yue` 的候选顺序：**越 / 月 / 约 / 跃 / 岳 / 悦 / 乐 / 曰**（「越」正好第一，搜"越来越不懂"很顺）
- 二进制表约 **32KB**，assets 分区（4MB，已用 1.74MB）完全放得下

⚠️ **只保留字库能显示的汉字**（与 charset.txt 取交集）：字库缺字在屏上是【一片空白】
（不是方框，见 [[esp-music-lcd-text-and-state]]），候选字里混进一个看不见的字，
用户选上去就是灾难。

## 已和用户确认的三个决定

1. **做屏上拼音输入法**（而不是只做字母直搜 / 也不是本地索引）
2. **播放页的 K4 保持现状**：短按换来源、长按进菜单 —— 播放页是最外层界面，
   没有"上一级"。其余页面改成新规则（短按回上一级、长按回播放器）。
3. **搜索结果页短按 K4 回【输入页】**（保留已输入内容，方便改几个字母重搜）；
   再按 K4 → 方式选择 → 再按 K4 → 主菜单；长按 K4 任何时候直接回播放器。

### 2. `UI_PAGE_SEARCH_IN`（输入页）—— 本次最大的一块

| 区域 | 内容 |
|---|---|
| 顶栏 0..20 | `搜索: <已输入的字母/汉字>` + 光标 |

| 候选区 ~34..88 | **仅拼音模式**：2 行 × 8 = 16 格候选字，16px 中文字体，窗口跟随光标 |
| 字母格 ~88..128 | 2 行 × 14 格 = 28 格：**A-Z + `退格`**（12px 拉丁字体）|

| 键 | 字母模式 | 拼音模式 |
|---|---|---|
| K1 / K2 短按 | 光标 ← / →（在 28 格里线性移动，越界不绕回） | 字母格内与字母模式相同；**在候选区则移动候选光标** |
| K3 短按 | 输入当前格子的字母（或执行退格） | 候选区：确定该候选字，追加到已输入汉字，清空音节回到字母格 |
| **K3 长按** | **开始搜索** | **开始搜索**（用已确认的汉字） |
| K4 短按 | 回上一级（方式选择页） | 同左 |
| K4 长按 | 回播放器（全局规则） | 同左 |

**拼音模式的音节判定**（决定何时切到候选区）：每输入一个字母后，用表判断：
- 该串已是一个**完整音节**、且**再追加任何字母都无法构成更长的音节** → 自动切到候选区
  （例：`yue` 不可再延长 → 直接出候选）
- 仍是更长音节的前缀 → 继续在字母格里输入（例：`yu` 还能是 `yuan`/`yun`，不急着出候选）
- 该串**不是任何音节的前缀** → 拒绝这个字母（保持原状，不把输入搞成死路）
- `退格` 格：删掉音节里最后一个字母；音节已空则删掉最后一个已确认汉字

**两种模式共用同一个输入页**：字母模式不显示候选区（那 54px 给已输入的大字/最近搜索留白），
K3 输入字母、长按 K3 直接搜（服务器模糊匹配英文/数字歌名）。

## player 侧：加搜索命令（UI 任务绝不能自己做网络）

搜索是阻塞网络调用（几百毫秒），按现有分层必须走命令层 ——
`player` 已经是"三路控制串行化"的地方，加一条命令最省事、也不破坏分层：

```c
/* player.h */
void player_search(const char *query);      /* 非阻塞：塞进命令队列，core0 执行 */
int  player_search_count(void);             /* 结果条数（0 = 没搜到） */
bool player_search_get(int idx, sub_song_t *out);
uint32_t player_search_gen(void);           /* 结果变化计数，UI 据此重建列表 */
bool player_search_busy(void);              /* 正在搜（UI 显示"搜索中…"） */
```
- 新增 `CMD_SEARCH`，在 `player_task` 里调 `subsonic_search()`，结果存 **PSRAM** 数组
  （64 × `sizeof(sub_song_t)` ≈ 24KB，和现有 `s_queue` 一样用 `heap_caps_*`）
- 用现成的 `s_lock` 保护；`player_search_gen++` 让 UI 知道该重画
- 播放选中那首：**`player_play_song(&song)`**（`player.h:64` 已有）——
  元数据已经在手，省一次 `getSong` 往返（⚠️ 它内部是 `play_song_meta()`：
  歌曲**不在队列里就追加到队尾再播**，所以 `player_queue_index()` 会指向那个追加槽位，
  而**不是**结果页的下标）。因此结果页的"正在播"指示**要按歌曲 id 比对**
  （`st.song_id` == 该行 id），不能按下标。
  （**这就是方案 A，不给 player 引 `player_src_t` 新枚举**，改动最小；
  代价是"播放搜索结果"会往当前队列尾部追加，之后按 K1/K3 切歌是在那个队列里走 ——
  可以接受，用户要的是"点了就能听"。）

## 拼音表：生成工具 + 运行时查表

**`tools/gen_pinyin.py`（新）**：
1. 读 `~/.local/share/fcitx5/rime/cn_dicts/8105.dict.yaml`，取**单字**条目 `汉字 拼音 权重`

```c
esp_err_t pinyin_init(void);                 /* mmap assets + 校验 magic，失败非致命 */
```

## 顺带修的两个 bug（本次发现，都与搜索无关但都在同一片代码里）

### 1. 搜不到东西时报 502
`get_song_list()`（`components/subsonic/src/subsonic.c`）在**解析成功但 0 条结果**时
`return ESP_FAIL`，于是 `/api/search` 走 `err != ESP_OK && got == 0` 分支返回 502。
实测：搜 `zzzznotexist` → `HTTP 502 {"error":"搜索失败（Navidrome 不可达？）"}`，
而真实情况是**服务器好得很，只是没这首歌**。
**修法**：`get_song_list()` 解析成功后一律返回 `ESP_OK`（0 条也是成功），
"取不到歌"交给调用方按 `got == 0` 判断。⚠️ 要顺带核对全部调用点：
`h_search`（改后自然返回 200 + 空列表）、`load_source`（已有 `got <= 0` → 退回随机 30 首 ✓）、
`h_random` / `h_starred` / `player_starred_refresh` 等。

### 2. ⚠️ 长按 K4 进菜单再回来，**封面消失**
`ui.c:481-513`：从别的页面回来时 `s_play_refresh_all = true` → 进 `force` 分支 →
那里**无条件把封面设回占位图**（`lv_image_set_src(s_img_cover, PLACEHOLDER)`）。
而真封面只在 `s_cover_ready && s_cover_gen == s_ui_gen` 时才贴（`ui.c:516`），
歌曲没变就不会重新触发 → **封面一直是占位图，直到下一首歌**。用户报的就是这个。
**修法**：`force` 分支里优先复用已经解码好的当前封面：
```c
if (s_cover_dsc.data != NULL && s_cover_gen == st.gen) {
    lv_image_set_src(s_img_cover, &s_cover_dsc);      /* 已经有这一代的封面，直接贴回 */
} else if (assets_get(ASSET_PLACEHOLDER_COVER_72, &ph)) {
    lv_image_set_src(s_img_cover, ui_img_dsc(ASSET_PLACEHOLDER_COVER_72));
}
```
（`s_cover_dsc.header.cf` 目前在异步到达分支里每次设，改成 `ui_start()` 里设一次更稳。）

## 明确不在本轮范围
