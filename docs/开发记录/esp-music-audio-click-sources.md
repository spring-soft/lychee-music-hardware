**2026-09-24** 调试 esp-music（`~/esp-music`）时把"咔哒声"逐一定位的结果。用户反馈"有咔嗒声"后，先怀疑固件，实际主因是**测试素材本身**。

**Why:** 这类问题十有八九被归到"驱动/时钟"上，白查很久。按下面的顺序排查最快——**先换干净的素材，再看代码**。

**How to apply:**

**① 最容易被误判的一类：测试素材硬切（本次的真凶）**
用 Python/脚本生成测试音频时，音符起音/收尾、静音边界如果直接跳变，每一处听起来就是一声"咔"。本次 12 秒的小星星里有 **28 处**，听起来像"周期性咔哒"，差点去查 PSRAM 带宽。
**修法**：每段音加 **5ms 淡入淡出**；生成后重编码（CBR MP3 大小不变是正常的，看 FLAC 大小有没有变来确认素材真的换了）。
**判据**：换成干净素材后咔哒消失 → 就不是固件问题。

**② 采样率切换没静音**（真问题）
`board_init` 按 48kHz 建 I2S，内容是 44.1kHz 时要在 DAC 还在输出时重配时钟 → 一声"咔"。
**修法**：`board_es8388_mute(true)`（写 0x19 bit2）→ 等 30ms → disable/reconfig/enable → 等 50ms → 取消静音。日志打"已静音过渡"。

**③ `i2s_channel_write` 部分写入未 commit**（真问题）
出错/超时但已写入一部分时若不 commit 那部分，下一轮会把同样的 PCM 再写一遍 → 波形重复一小段 = 咔哒。
**修法**：**无论返回什么，只要 `w > 0` 就 commit**。

**④ `audio_ring_defrag()` 与生产者并发**（潜在，M2 走网络流必踩）
defrag 会重置 rd/wr，而生产者可能正拿旧 wr 往同一区域写 → 数据错位。
**修法**：只在 `s_fetch_eof`（生产者已停）时才 defrag；流还在来时靠 `simple_dec` 自己吃下被回绕切开的帧。

**⑤ 测试音相位跨调用保持**（真问题，仅影响测试信号）
`static float phase` 让每次起音落在非零相位 → 起音一声咔。改为**每次调用从 0 开始** + 5ms 包络。

**另一个测量陷阱：WS 频率要用 100ms 窗口**
20ms 窗口的量化误差能到 ±几百 Hz，会误报成"时钟不准"（实测 44.1k 用 20ms 量到 43100，用 100ms 量是 43910 = 偏差 -0.43%，属正常 PLL 舍入，7 音分听不出来）。
