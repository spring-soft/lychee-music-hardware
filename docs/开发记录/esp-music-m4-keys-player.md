**2026-09-25 完成 esp-music 的 M4**（按键 + 列表页/菜单页/音量页 + 来源切换），设备已能日常用。启动到出声 **3.8 秒**（新住处这个网 RSSI -28、Navidrome 同网段，比上一版 5.1 秒更快）。

**Why:** 三路控制（按键 / 网页 M5 / 蓝牙 M7）如果各自直接调 `audio_engine_*`，一定会出现"两个任务同时换歌、队列各说各话"。所以 M4 的主要产出不是页面，而是**命令层**——页面和按键都只是它的调用方。

**How to apply：**

**1. `components/player/` 是唯一的播放控制入口**（不是 UI 的一部分）
- 所有控制都是 `player_xxx()` → 往一条 FreeRTOS 队列塞命令（非阻塞），只有 `player` 任务（**core 0 / prio 5**）碰 `audio_engine` 和队列 → 天然串行。
- **core 0 是故意的**：命令里要做 HTTP（拉歌单/开流，几百毫秒），放 core 1 会阻塞 UI。
- 队列 64 首 + 最近播放 50 条都在 **PSRAM**（内部 SRAM 只留协议栈/任务栈/DMA）。
- 换歌序列：`board_es8388_mute(true)` → `audio_engine_stop()` → 等 60ms 让 DMA 里旧音频放完 → 建新源 → `audio_engine_play()` → 解除静音 → 才能 `free` 旧源。**不加静音会听到断点"咔"**。

**2. 键位表（M4 定稿）**

| 页面 | 短按 | 长按 |
|---|---|---|
| 播放页 | K1 下一首 · K2 播放暂停 · K3 上一首 · **K4 循环来源（立刻播）** | K1 收藏/取消 · K2 音量页 · K3 列表页 · K4 菜单 |
| 列表页 | K1 上一行 · K2 下一行 · K3 播放选中 · K4 回播放页 | K1/K2 连滚（160ms 节流） |
| 菜单页 | K1 上 · K2 下 · K3 确认 · K4 回播放页 | — |
| 音量页 | K1 −5% · K2 静音 · K3 +5% · K4 回播放页 | K1/K3 连调 |

- 长按判定 **700ms**（太短会在"想连按两下下一首"时误触发收藏）。
- 菜单 6 项填满 6 行（正好不用滚动）：3 个来源 + 播放/暂停 + 屏幕亮度 + 系统信息。
- **列表页 K1/K2 长按不能同时是"切来源"又是"连滚"**——`LONG_PRESS_START` 之后 `LONG_PRESS_HOLD` 会持续触发，两个动作会一起发生。这是把原方案的"长按切来源"挪走的原因。
- ⚠️ **K1 在 GPIO3（strapping 脚）**：开机瞬间按住它会进 JTAG 下载模式。
- 音量页的"亮度"模式复用同一屏（`ui_vol_set_mode(true)`），亮度下限夹在 5% 免得黑屏看不见。

**3. 来源只有三个**：最近播放（**本机环形缓冲，M6 才落盘，现在重启即丢**）/ 我的收藏（`getStarred2`）/ 随机 30 首（`getRandomSongs`）。原方案的第四个"当前歌单"砍掉了——它需要先做歌单浏览 UI，价值不如前三个；服务器歌单留给 M6 和网页控制台。

**4. 性能实测**：`lv_timer` 最坏 4~45ms，刷新量 5~9 次/5s（整屏=40KB）。45ms 尖峰是已知的 flash-cache/PSRAM 竞争（记在 M8），不是重绘问题。

**⚠️ 5. 内部 SRAM 只剩 29KB（M7 加蓝牙前必须处理）**
开机 `内存[after]` 是 78KB 空闲，但起播后掉到 **29KB 并稳定在那里**（WiFi 已连的情况下又少了 49KB = HTTP 流 + 解码器状态）。BLE/NimBLE 要 ~40KB，**按现在这样直接加会失败**。可选办法：给 `esp_audio_simple_dec` 的分配想办移到 PSRAM、调小 `CONFIG_SPIRAM_MALLOC_ALWAYSINTERNAL`、或裁剪 NimBLE 缓冲。PSRAM 那边很宽裕（6783KB 空闲）。

## 第二轮反馈：持久化 + 系统信息页（2026-09-25 当天）

用户要求："**在设置里做的调整都要持久化保存，包括后面的网页控制台也一样**"，
外加"系统信息根本显示不全，要能显示本机 IP"。

**1. 新建 `components/settings/` —— 全工程唯一的设置落盘入口。**
之前音量在 player 里存、亮度在 UI 里存，各写一份"2 秒去抖"；M5 网页还要存 WiFi 凭据和
Navidrome 账号 —— 会变成四处重复，而且**去抖这个约束靠每个调用点自觉是不可靠的**。现在：

| 场景 | 用哪个 |
|---|---|
| 高频调整（音量/亮度/来源） | `settings_set_int_lazy(key, v)` → 静置 2 秒才落盘；由 `settings_tick()` 刷 |
| 一次性动作（网页点"保存"） | `settings_set_int()` / `settings_set_str()` 立刻落盘 |

- NVS 命名空间 **`cfg`**（不是 `ui` 也不是 `vol`），键：`vol` / `bright` / `src`。
  M5 的 `ssid`/`pass`/`nav_host`/`nav_user`/`nav_pass` 也放这里。
- `settings_tick()` 挂在 **player 任务的循环**里（200ms 周期）；UI 任务不写 NVS。
- `settings_pending_count()` 给系统信息页显示"设置待存 N"。
- 注意 `nvs_flash_init()` 是 `net_mgr_init()` 负责的，`settings_init()` 只开命名空间；
  调用顺序必须是 `net_mgr_init()` → `settings_init()` → `player_init()` / `ui_start()`。
- ⚠️ 别把值打进日志：这个接口存 WiFi/Navidrome 密码，只打键名和字节数。

**2. 「来源」也持久化了**，重启沿用上次的来源。**配套必须做保底**：
重启时那个来源可能已经取不到歌（最近播放重启后是空的、收藏被清空），
所以 `handle_set_source()` 里取不到歌要**自动退回随机 30 首**，否则设备开机就是哑巴。

**3. 系统信息从一行 toast 改成整页**（`UI_PAGE_INFO` + 新的 `bg_info.png`，7 行 × 15px）。
一行 toast 只有 138px 宽，`RAM 31K | 欠载 0 | 192.168.110.17` 根本放不下（用户原话"根本显示不全"）。
新页 7 行：**本机 IP** / WiFi(SSID+RSSI) / 内存 / 音频(采样率+欠载+I2C重试) / 音量+静音+亮度 /
曲目位置+来源 / 运行时长+待存设置数。
**教训：一行装不下的事实别硬塞 toast —— 用户看到的是"显示不全"，不是"信息太多"。**
纯展示页的按键处理：**任何键都回播放页**（`ui_keys.c` 里单独一个 case，别掉进 default 什么都不做）。

## M4 上机后的一轮反馈修正（2026-09-25 当天）

用户试完报回 5 条，逐条落地的结论：

1. **⚠️ 上屏字符串只能用字库里的字符。** 字库 `tools/gen_font.sh` 生成的是 **GB2312 全集 + 中文标点 + 全角符号 + 0x2010-0x203B**，
   `★`(U+2605) `▶`(U+25B6) `♪`(U+266A) `●` `▸` **全都不在里面** → 屏上显示成方框。
   用户的报法很典型："在列表里选择歌曲后确认时有一个字符没正常显示"（就是 `"▶ %.40s"`）。
   **改动前先跑这个自查**（只查会进 `ui_toast`/`ui_put_label` 的串，串口日志里的符号无所谓）：
   逐字符对照 `assets_src/font/charset.txt` + ASCII。
2. **音量/亮度必须持久化**（用户要求"重启后音量要长期保持在"）：NVS 命名空间 `ui`，
   键 `vol` / `bright`，**2 秒去抖**后再 `nvs_commit`（音量页长按连调很密，不去抖会写爆 NVS）。
   音量存在 player 任务的循环里落盘，亮度在 UI 任务的 `ui_pages_tick` 里落盘。
   注意 `board_backlight_set()` 要等 `board_backlight_init()` 之后才能调 —— 所以亮度恢复单独走
   `ui_pages_apply_brightness()`，在 ui.c 里背光初始化之后调用。
3. **"静音"必须是真静音**：之前音量页 K2 只是把音量设成 0（模拟 -45dB + 数字 -15dB，总 -60dB），
   用户说"不是真静音"。现在走 `board_es8388_set_mute()` → DACCONTROL3 bit2 硬静音。
   **坑**：切歌和换采样率都会临时静音再解开，如果直接 `board_es8388_mute(false)` 会把用户设的静音冲掉 ——
   所以板级要有一个**粘住**的 `s_user_muted`，`es_mute_apply()` 在临时静音结束后恢复它，
   `i2s_reconfig()` 结尾也用 `es_mute_apply()` 而不是 `board_es8388_mute(false)`。
4. **音量页键位改成 K1=加、K3=减**（原来是反的，用户指定）。
   顺带：按"加"时自动取消静音（用户按加显然是想听），`ui_vol_step(+5)` 里判的。
5. **底噪** —— 用户后来表示"别查了就这样吧"，停止排查。已落地的**唯一**相关改动：
   **ES8388 的 ADC + line-in 断电**。厂商给 `k_es8388_init[]` 表里**根本没有 `0x03` 这条**，
   所以芯片复位默认值 `0xFC`（ADC 通电）一直有效 —— 而我们从不录音。
   `esp_codec_dev` 驱动在 DAC-only 场景写的正是 `0xFF`（注释 "power down adc and line in"），
   `ADCPOWER(0x03)` 是**反逻辑：位=1 表示断电**。加进去后 dump 确认 `03=FF`。
   另外 MCLK 抖动这条路在 S3 上是死的，见 [[esp32s3-i2s-no-apll]]。

**同一轮的工具教训**：`sdkconfig.local` 改了不生效（[[esp-music-sdkconfig-local-trap]]）；
回退路径（WiFi 没连上 → 放内嵌测试音）忘了调 `ui_splash_finish()`，启动页会一直挂在第 5 步，
看起来像死机 —— **加回退分支时记得它也要收尾启动页**。

菜单最终 7 项（屏上 6 行，窗口自动滚最后一项）：
`来源:最近播放 / 来源:我的收藏 / 来源:随机30首 / 播放暂停 / 屏幕亮度 / 重连WiFi / 系统信息`。
"重连 WiFi" 是因为自动重连 8 次失败后就彻底放弃（换地方/路由器重启会触发），
`net_mgr_reconnect()` 是唯一的手动救回入口，否则只能重启设备。

## ⚠️⚠️ 改按键/页面跳转前必读：K4 只能在一个地方判 + 怎么自己验

**同一个坑我连踩三次**（2026-09-25）：
1. **蓝牙控制页"没连上就把按键吃掉"那段把 K4 一起吞了** → 用户卡在遥控页出不来
2. **搜索页我特意让 K4"放行"，但 `key_short` 里没写搜索页的 case** → 掉到 `default`
   **什么都不做** → 用户搜完歌按 K4 回不去
3. 更早还有"来源二级菜单长按 K4 单独特判"（和其它页面规则不一致）

根因都是**规则散在每个页面里，改一处漏一处**。现在的做法：
**`ui_keys.c` 里一个 `k4_navigate(k, long_press)`，在最前面判一次**，规则是
短按回 `ui_page_parent(当前页)`、长按直接回播放器、**播放页例外**
（最外层，短按换来源/长按进菜单，用户确认保持）。各页面自己的 K1/K2/K3 处理里
**不要再碰 K4**。另外：**离开蓝牙控制页要顺带 `hid_remote_set_mode(false)`** ——
不关的话 `ui_bt_mode_follow()` 会把页面又拉回去（长按 K4 会变成拉锯）。

**教训一句话：写任何"吞掉按键"的逻辑之前，先问"出口键(K4)会不会被一起吞掉"。**

## 不用手也能验证按键：`K4_SELFTEST` 编译开关（`main/app_main.c`）
我看不见屏幕、也按不到按键，而上面那些问题**靠读代码已经栽了三次**。所以做了这个：
改成 `1` 烧一次，固件开机后自己把按键序列打一遍（`ui_keys_inject()` 走的是和真实
按键**完全相同**的分发函数），每一步打印 `按键前=页面名 -> 按键后=页面名`，
需要时再调 `ui_search_debug_dump()` 打出输入页内部状态（模式/已输入/音节/光标/候选）。
**读串口就能验证整条导航链**，比让用户按一遍快得多也准得多。

实测那 18 步把"蓝牙页退出""搜索各级返回""K1 向右""输入字母""长按K3搜索"全覆盖了。
⚠️ **平时必须是 0**（开着它会在开机后自己乱按键）。
（`ui_page_name()` 也是这次加的 —— 日志里看页面编号太费劲。）
